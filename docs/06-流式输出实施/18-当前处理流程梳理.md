# 当前处理流程梳理

> 面向当前这套 `frontend-vue + scheduler-go + openclaw-pool + Ollama` 链路，梳理请求从前端进入到模型返回的完整处理流程，并说明目前问题收敛到了哪里。

---

## 🎯 目的

这份文档只回答三个问题：

1. **现在的处理链路到底是什么？**
2. **每一层当前负责什么？**
3. **“看起来像非流式” 的根因目前定位到哪里？**

---

## 🏗️ 当前整体链路

```text
浏览器前端
  ↓ POST /api/chat/stream
Frontend Nginx
  ↓ 反向代理 /api → scheduler-go
Scheduler (Gin SSE)
  ↓ 分配容器 + 准备智能体
  ↓ WebSocket 连接 OpenClaw Gateway
OpenClaw Gateway
  ↓ chat.send
  ↓ agent/chat 事件广播
OpenClaw Agent Runtime
  ↓ 调用模型 Provider
Ollama
```

当前系统中，真正的“跨组件协议”分成两段：

- **前端 ↔ Scheduler**：HTTP SSE
- **Scheduler ↔ OpenClaw Gateway**：WebSocket RPC + Event

也就是说，前端并不是直接连 OpenClaw，而是先经过 Scheduler 做容器调度和协议转换。

---

## 1️⃣ 前端层：发起请求并消费 SSE

前端入口是 [App.vue](file:///Users/lifeng/git/git-claw/agent-openclaw-assisant/frontend-vue/src/App.vue)。

当前前端做的事情：

- 向 `/api/chat/stream` 发起 POST 请求
- 接收 SSE 数据流
- 解析 `data: ...` 事件
- 处理状态消息、错误消息和 OpenAI 兼容 chunk
- 把 `choices[0].delta.content` 追加到页面显示

这一层我们已经验证过：

- 状态事件是即时到达的
- heartbeat 注释帧能即时到达
- 如果 Scheduler 连续吐出多个 chunk，前端是能逐段显示的

因此，**前端不是当前瓶颈**。

---

## 2️⃣ Nginx 层：只做代理，不做业务处理

前端容器里的 Nginx 负责两件事：

- 提供 Vue 静态页面
- 把 `/api` 转发给 Scheduler

当前和流式相关的关键配置已经关闭缓冲：

- `proxy_buffering off`
- `proxy_cache off`
- 长连接超时拉长

这意味着 Nginx 当前的职责只是“转发已产生的数据”，不会主动把已经写出的 chunk 合并后再统一返回。

因此，**Nginx 不是当前根因**。

---

## 3️⃣ Scheduler 层：容器调度 + 协议转换

核心处理逻辑在 [api.go](file:///Users/lifeng/git/git-claw/agent-openclaw-assisant/scheduler-go/internal/api/api.go#L470-L733)。

### 3.1 处理流程

当前 `/api/chat/stream` 的处理顺序如下：

1. 解析前端传来的 `agent_id` 和 `message`
2. 立即建立 SSE 响应头并给前端发送状态消息
3. 调用容器分配逻辑，选出一个可用 `openclaw-pool` Pod
4. 调用 `EnsureAgentReady`，确保目标 agent 已注册到容器中
5. 通过 WebSocket 连接 OpenClaw Gateway
6. 发送 `chat.send`
7. 持续监听 OpenClaw 返回的 `res / agent / chat` 事件
8. 转换成前端能消费的 SSE chunk
9. 最终发送 `[DONE]`

### 3.2 当前事件处理策略

Scheduler 现在优先消费两类事件：

- **agent 事件**
  - `stream = "assistant"` 时，优先取 `data.delta`
  - 这是最接近真实流式文本的来源
- **chat 事件**
  - `state = "delta"` 时，作为兜底补全
  - `state = "final"` 时，作为结束信号

对应代码见：

- [writeSSEChunk](file:///Users/lifeng/git/git-claw/agent-openclaw-assisant/scheduler-go/internal/api/api.go#L447-L468)
- [agent 事件处理](file:///Users/lifeng/git/git-claw/agent-openclaw-assisant/scheduler-go/internal/api/api.go#L653-L669)
- [chat 事件兜底与完成处理](file:///Users/lifeng/git/git-claw/agent-openclaw-assisant/scheduler-go/internal/api/api.go#L672-L717)

### 3.3 当前结论

Scheduler 这一层已经具备“收到多少段，就往前端推多少段”的能力。

也就是说：

- 如果 OpenClaw 连续发 10 个 delta
- Scheduler 会连续输出 10 个 SSE chunk

因此，**Scheduler 不再是当前主要瓶颈**。

## 4️⃣ OpenClaw Gateway 层：WebSocket chat.send 与事件广播

### 4.1 Scheduler 当前调用的是哪条链路

Scheduler 不是调用 OpenClaw 的 HTTP OpenAI 兼容接口，而是直接走 WebSocket 的 `chat.send`。

这条链路的价值是：

- 能复用 Control UI 同一套 Gateway 事件体系
- 能直接拿到 `agent` 和 `chat` 事件
- 不依赖 OpenAI HTTP 适配层二次封装

### 4.2 Gateway 内部会做什么

OpenClaw Gateway 收到 `chat.send` 以后，会：

1. 校验 `sessionKey / message / idempotencyKey`
2. 创建这次会话的运行上下文
3. 调用 Agent Runtime 执行
4. 把运行时事件广播成：
   - `agent` 事件
   - `chat` 事件

相关代码：

- `chat.send` 入口：[chat.ts](file:///Users/lifeng/git/git-claw/agent-openclaw-assisant/workspace/source/openclaw/src/gateway/server-methods/chat.ts#L876-L903)
- Control UI 事件转发：[server-chat.ts](file:///Users/lifeng/git/git-claw/agent-openclaw-assisant/workspace/source/openclaw/src/gateway/server-chat.ts#L341-L391)
- Control UI 监听 assistant 事件并转 chat delta：[server-chat.ts](file:///Users/lifeng/git/git-claw/agent-openclaw-assisant/workspace/source/openclaw/src/gateway/server-chat.ts#L593-L600)

## 5️⃣ Control UI 为什么“看起来是流式”

Control UI 的客户端逻辑在：

- [handleChatEvent](file:///Users/lifeng/git/git-claw/agent-openclaw-assisant/workspace/source/openclaw/ui/src/ui/controllers/chat.ts#L262-L335)

它的显示机制是：

- 收到 `state = "delta"` 时，不断更新 `chatStream`
- 收到 `state = "final"` 时，把最终消息写入聊天记录

因此，只要 Gateway 连续广播多个 `chat delta`，Control UI 就会连续刷新，看起来是流式输出。

但是需要注意：

- **Control UI 能流式显示**，不等于 **当前运行时一定在持续产出多个 assistant delta**
- 它只是“支持流式渲染”

## 6️⃣ 直接测试 OpenClaw 原生接口后的结果

为了排除外围组件干扰，已经直接测试了 OpenClaw 原生接口。

### 6.1 直接测 HTTP `/v1/chat/completions`

现象：

- 先返回 assistant role chunk
- 再一次性返回完整正文
- 最后 `[DONE]`

这说明 OpenAI 兼容 HTTP 接口在当前环境下，**并没有稳定多段输出正文**。

### 6.2 直接测 WebSocket `chat.send`

现象：

- 请求发出后等待约 23 秒
- 只收到 **1 个** `agent stream=assistant delta`
- 该 delta 已经是完整长文
- 随后立刻收到 final

这比前端、Scheduler 更靠近上游，因此说明：

- 问题不是前端显示合并
- 也不是 Scheduler 二次合并
- 而是 **OpenClaw 当前运行时实际只发出了一次 assistant delta**

---

## 7️⃣ 当前根因收敛

到目前为止，问题已经从“是不是前端没处理好流式”收敛为：

### ✅ 已排除

- 前端 SSE 解析问题
- Nginx 代理缓冲问题
- Scheduler SSE flush 问题
- Scheduler WebSocket 转 SSE 的协议转换问题

### ⚠️ 当前最可疑位置

- OpenClaw `chat.send` 对应的运行链路
- Agent Runtime 到 Gateway 事件总线之间
- 或模型 Provider 输出到 assistant 事件的聚合阶段

一句话总结就是：

> **不是下游把流式合并了，而是上游当前就没有稳定地产生多段 assistant delta。**

## 8️⃣ 当前处理流程图

```text
用户在前端输入消息
  ↓
前端 POST /api/chat/stream
  ↓
Nginx 转发到 Scheduler
  ↓
Scheduler 发送状态消息给前端
  ↓
Scheduler 分配 openclaw-pool Pod
  ↓
Scheduler 确保 Agent 已注册
  ↓
Scheduler 通过 WebSocket 连接 OpenClaw Gateway
  ↓
Scheduler 发送 chat.send
  ↓
OpenClaw Gateway 调用 Agent Runtime
  ↓
Agent Runtime 调用 Ollama
  ↓
OpenClaw 返回 agent/chat 事件
  ↓
Scheduler 转成 SSE chunk
  ↓
前端逐段显示
```

当前真正的问题点在这一步：

```text
Agent Runtime / Gateway
  ↓
assistant delta 没有稳定分多段产生
```

---

## 9️⃣ 下一步建议

下一步不应该继续优先查 Nginx 或前端，而应该继续向 OpenClaw 上游追：

1. 检查 `ollama-stream.ts` 到 assistant 事件之间的传递路径
2. 检查 Agent Runtime 是否把 token 聚合后才 emit
3. 检查 Gateway 的事件总线是否在某处做了节流或合并
4. 必要时直接在 OpenClaw 源码里对 assistant 事件打日志，确认每次 emit 的内容和时机

---

## 🔚 结论

当前这套系统的处理流程已经比较清晰：

- 前端负责接收 SSE 并渲染
- Nginx 只做代理
- Scheduler 负责容器调度、Agent 准备、WebSocket 调用和 SSE 转换
- OpenClaw Gateway 负责 `chat.send` 和事件广播
- 真正决定“是不是多段流式”的，是 OpenClaw Runtime 产出的 `assistant delta`

目前的结论不是“系统完全不支持流式”，而是：

> **系统链路已经支持流式，但当前这套 OpenClaw 运行时在实际执行时，返回的 assistant delta 仍然经常只有一段。**
