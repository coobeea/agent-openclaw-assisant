## 🔄 数据流图 (Chat Stream)

```
1. 用户发送消息
   Browser → Nginx (/)
   
2. 前端调用 API
   Vue3 → POST /api/chat/stream
   Body: {"message":"你好","agent_id":"main"}
   
3. Nginx 代理
   Nginx → http://scheduler:8080/api/chat/stream
   
4. Scheduler 分配容器
   Scheduler → 查询空闲 Pod
   Scheduler → 选择 openclaw-pool-xxx (10.1.0.203)
   
5. Scheduler 调用 Gateway
   Scheduler → POST http://10.1.0.203:18789/v1/chat/completions
   Header: Authorization: Bearer openclaw123
   Body: {
     "model":"gemma4:e4b",
     "messages":[{"role":"user","content":"你好"}],
     "stream":true
   }
   
6. OpenClaw Gateway 创建 Agent  
   Gateway → agentCommandFromIngress()
   Gateway → subscribeEmbeddedPiSession()
   Gateway → onAgentEvent(evt => writeSse(res, evt))
   
7. OpenClaw Agent 调用 LLM
   Agent → HTTP POST http://host.docker.internal:11434/api/chat
   Ollama → 流式返回 tokens
   
8. OpenClaw 处理响应
   parseNdjsonStream(ollamaResponse) ✅ 流式
     ↓
   stream.push({type:"text_delta", delta:"你"}) ✅ 流式
     ↓
   emitAgentEvent({stream:"assistant", delta:"你"}) ⚠️ 聚合
     ↓
   onAgentEvent() → writeSse() ❌ 延迟触发
   
9. Scheduler 转发 SSE
   resp.Body.Read(1 byte) → 检测 \n → Flush() ✅ 实时
   
10. Nginx 转发
    proxy_buffering off ✅ 实时
    
11. 浏览器接收
    EventSource.onmessage ✅ 实时
```

## 📦 容器热池策略

### 当前实现（Phase 1）
- **固定副本数**: 3 个 OpenClaw Pod
- **简单轮询**: Scheduler 按顺序分配
- **无状态**: 每次请求独立分配

### 未来扩展（Phase 2+）

#### 1. 容器重用（多用户共享）
```
当智能体数量 > 可用容器数时：

策略 A - 单 Agent 单容器（隔离性高）
  - 每个容器只服务 1 个 Agent
  - 需要动态扩缩容 (HPA)
  - 适合付费用户/企业版
  
策略 B - 多 Agent 单容器（成本低）
  - 1 个容器服务多个 Agent
  - OpenClaw 原生支持（/data/agents/agent-{id}/）
  - Scheduler 维护 Pod → AgentIDs 映射
  - 适合免费用户/社区版
  
推荐: 策略 B + 按需扩容
  - 默认 3 Pod，每 Pod 最多 10 Agents
  - 超过 30 个 Agent 时触发 HPA 扩容
  - 通过 Session 亲和性保证同一用户请求路由到同一 Pod
```

#### 2. 容器回收（闲置资源释放）
```yaml
回收策略:
  - 检测周期: 每 5 分钟
  - 闲置阈值: 30 分钟无请求
  - 回收动作:
    1. Scheduler 标记 Agent 为 "idle"
    2. 删除 Pod 中的 Agent 工作区: rm -rf /data/agents/agent-{id}
    3. 从映射表移除: AgentMap.delete(agentId)
    4. 如果 Pod 无任何 Agent，可选：Pod 缩容（HPA）

持久化数据:
  - PostgreSQL: Agent 配置、用户数据
  - MinIO: 对话历史、上传文件
  - Redis: Session、临时缓存
  
恢复策略:
  - 用户再次请求 → Scheduler 检测 Agent 不存在
  - 从 PostgreSQL 加载配置 → 重新创建 Agent
  - 从 MinIO 加载历史 → 恢复上下文
```

#### 3. Workspace 挂载（数据持久化）
```yaml
当前方案（临时存储）:
  volumes:
    - name: agent-workspace
      emptyDir: {}  # Pod 重启后数据丢失
  
  volumeMounts:
    - name: agent-workspace
      mountPath: /data/agents
      
问题:
  - Pod 重启/删除 → Agent 数据丢失
  - 无法跨 Pod 共享数据
  
解决方案 A - hostPath (单节点开发)
  volumes:
    - name: agent-workspace
      hostPath:
        path: /Users/lifeng/.../workspace/lobsters
        type: DirectoryOrCreate
        
  优点: 简单，适合开发
  缺点: 仅限单节点，生产不可用
  
解决方案 B - NFS/Ceph (多节点生产)
  volumes:
    - name: agent-workspace
      persistentVolumeClaim:
        claimName: openclaw-agents-pvc
        
  PVC 配置:
    kind: PersistentVolumeClaim
    spec:
      accessModes: [ReadWriteMany]  # 多 Pod 同时读写
      storageClassName: nfs-client
      resources:
        requests:
          storage: 100Gi
          
  优点: 支持多节点，高可用
  缺点: 需要搭建 NFS/Ceph 集群
  
解决方案 C - S3/MinIO (对象存储)
  - 代码文件、配置 → 直接存 MinIO
  - 运行时临时文件 → emptyDir
  - Agent 启动时从 MinIO 下载必要文件
  
  优点: 云原生，弹性伸缩
  缺点: 需要修改 OpenClaw 代码适配

推荐方案:
  开发: hostPath
  生产: NFS/Ceph PVC
  云上: S3/MinIO 对象存储
```

## 🚀 扩展性分析

### 当前容量（单节点开发）
- 最大并发用户: ~10 (每 Pod 服务 1-2 个 Agent)
- 响应时间: 6-12 秒/请求
- 瓶颈: OpenClaw Pod 内存（1Gi/Pod）

### 生产扩展（多节点集群）
- HPA 自动扩容: 3-20 Pod
- 每 Pod 服务: 5-10 Agent
- 最大支持: ~100 并发 Agent
- 成本优化: 闲置回收 + Spot 实例

## 📝 部署模式总结

| 模式 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| Docker Desktop K8s | 本地开发 | 快速迭代 | 单节点，性能受限 |
| Minikube/Kind | CI/CD 测试 | 环境一致 | 不支持生产 |
| 云托管 K8s (EKS/GKE/AKS) | 生产环境 | 高可用，弹性 | 成本较高 |
| 自建 K8s (Kubeadm/Rancher) | 私有云/IDC | 完全可控 | 运维复杂 |
