## 💡 根本原因

### 代码分析

查看 `scheduler-go/internal/api/api.go` 的 `ChatStream` 函数：

```go
// 6. 通过 WebSocket 发送聊天请求
chatReq := map[string]interface{}{...}

fmt.Printf("📡 [ChatStream] 发送 WebSocket 请求...\n")
if err := conn.WriteJSON(chatReq); err != nil {
    fmt.Printf("❌ [ChatStream] 发送请求失败: %v\n", err)
    c.JSON(http.StatusInternalServerError, gin.H{"error": "发送请求失败"})
    return
}

// 7. 实时监听 WebSocket 事件并转换为 SSE
fmt.Printf("⏳ [ChatStream] 开始监听 WebSocket 事件...\n")  ← 这行没有执行！
```

**问题**: 在发送 WebSocket 请求后，代码**卡住了**，没有继续执行！

### 可能的原因

1. **WriteJSON 阻塞**: WebSocket 写入阻塞（缓冲区满？）
2. **响应头问题**: SSE 响应头设置有问题，导致客户端不接收数据
3. **Gin Context 问题**: HTTP 响应被提前关闭

---

## 🔧 解决方案

### 方案 1: 添加详细日志（诊断）

```go
func ChatStream(c *gin.Context) {
    // ... 之前的代码 ...
    
    fmt.Printf("📡 [Before WriteJSON] 准备发送请求\n")
    err := conn.WriteJSON(chatReq)
    fmt.Printf("📡 [After WriteJSON] 发送完成, err=%v\n", err)
    
    if err != nil {
        fmt.Printf("❌ [ChatStream] 发送请求失败: %v\n", err)
        c.JSON(http.StatusInternalServerError, gin.H{"error": "发送请求失败"})
        return
    }
    
    fmt.Printf("⏳ [ChatStream] 开始监听 WebSocket 事件...\n")
    // ...
}
```

### 方案 2: 检查 SSE 响应头设置

**当前代码**:
```go
c.Header("Content-Type", "text/event-stream; charset=utf-8")
c.Header("Cache-Control", "no-cache")
c.Header("Connection", "keep-alive")
c.Header("X-Accel-Buffering", "no")
c.Status(http.StatusOK)  ← 这里！

flusher, ok := c.Writer.(http.Flusher)
flusher.Flush()
```

**问题**: `c.Status(http.StatusOK)` 可能没有真正发送响应头。

**修复**:
```go
c.Header("Content-Type", "text/event-stream")
c.Header("Cache-Control", "no-cache")
c.Header("Connection", "keep-alive")
c.Header("X-Accel-Buffering", "no")

// 立即写入一些数据，确保响应头发送
flusher, ok := c.Writer.(http.Flusher)
if ok {
    // 发送初始事件，触发响应头
    fmt.Fprintf(c.Writer, "data: {\"type\":\"init\"}\n\n")
    flusher.Flush()
}
```

### 方案 3: 异步处理 WebSocket（推荐）

**问题**: 可能是 Gin 的上下文在等待过程中被释放。

**解决**: 使用 goroutine 处理 WebSocket 事件，主线程专注于 SSE 输出。

```go
func ChatStream(c *gin.Context) {
    // ... 设置 SSE 响应头 ...
    
    // 创建通道传递事件
    eventCh := make(chan StreamEvent, 100)
    doneCh := make(chan bool)
    
    // Goroutine 1: 监听 WebSocket
    go func() {
        defer close(eventCh)
        for {
            var frame map[string]interface{}
            if err := conn.ReadJSON(&frame); err != nil {
                return
            }
            // 解析并发送到通道
            eventCh <- parseFrame(frame)
        }
    }()
    
    // Goroutine 2: 转换为 SSE 并发送
    for {
        select {
        case event, ok := <-eventCh:
            if !ok {
                return
            }
            // 转换为 SSE 并 Flush
            fmt.Fprintf(c.Writer, "data: %s\n\n", event.ToJSON())
            flusher.Flush()
            
        case <-doneCh:
            return
        }
    }
}
```

## 💭 反思

**为什么改了这么久还不行？**

1. **架构是正确的**: WebSocket + SSE 的设计没问题
2. **连接是成功的**: WebSocket 能建立，Ollama 能响应
3. **问题很隐蔽**: 卡在一个不起眼的地方（WriteJSON 后）

**真正的问题**:
- 不是技术选型问题
- 不是网络连接问题
- 是**代码执行流程中的阻塞问题**

这种问题很难发现，因为：
- 没有报错
- 连接正常
- 只是"卡住"了

**解决关键**: 详细的日志 + 异步处理
